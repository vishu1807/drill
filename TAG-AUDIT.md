# Tag History Audit

The existing tags mix naming styles, point at conflicting or misleading targets, and do not consistently describe a release. The evidence below comes from `git tag`, the decorated commit history, the tag object types, and the repository's deployment and release records.

| Evidence | Problem | Team impact and rollback/traceability risk |
| --- | --- | --- |
| `release_2` points to `28bd110`, the same commit as `version-1.0`. | This is a lightweight, unannotated tag with an opaque name, and the incident log says the team used it as a rollback target even though it pointed to an older unsupported commit. | Responders cannot tell which release or change `release_2` represents, or why it is safe. A rollback can restore the wrong code, and the missing annotation leaves no release rationale to audit. |
| `version-1.0` also points to `28bd110`. | The tag uses neither the agreed `vMAJOR.MINOR.PATCH` format nor a unique release identity; it aliases `release_2` despite implying a different release. | Operators may pick either label for the same commit while assuming they represent different releases. Release records and rollback instructions cannot reliably identify one canonical version. |
| `stable-build` and `v1.4.2` both point to `ff1fb9a`. | `stable-build` is a non-versioned label that duplicates `v1.4.2`; the commit is the repository scaffold, not evidence of the features claimed in the old notes. | “Stable” is subjective and cannot be ordered or matched to a deployment. The version alias gives false precision, increasing the risk of rolling back to a scaffold instead of the intended production build. |
| `v1.4.2` points to `ff1fb9a`, whose `src/app.js` is a placeholder. | The old release notes claim payment token caching and checkout-timeout fixes, but the tagged commit contains only the placeholder checkout service. | The tag does not substantiate the changes associated with that release. Auditors cannot establish what was deployed, and responders could roll back expecting fixes that are not in the tagged code. |
| `v2-final-FINAL` and `patch-new` both point to `82535d9`. | The labels are not semantic versions, and “final” is duplicated while “patch” provides no patch number. | The team cannot reliably compare this release with prior or later releases or know which label to use in deployment records; rollback instructions become ambiguous. |
| `1.5.0` points to `86989b6` but omits the required `v` prefix. | This annotated tag resembles a version but is inconsistent with `v1.4.2`, and the old notes make claims not established by this tag's one-line documentation edit. | Scripts and people looking for canonical `v`-prefixed releases can miss or misorder it. The apparent version number can also be mistaken for proof of shipped functionality. |
| `latest-good` points to `da6b2ed`. | “Latest” and “good” are mutable, subjective assertions rather than an immutable version identity; the deployment history records a production deployment under this label without identifying its version. | A responder cannot determine which build was considered good or whether the label still names that build. That weakens both repeatable rollback and the audit trail for the deployment. |

These legacy tags are retained as historical evidence. The canonical releases introduced in this change use annotated `vMAJOR.MINOR.PATCH` tags and are mapped to specific commits below.
